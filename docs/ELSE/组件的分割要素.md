组件作为前端的必备技能，组件分割的粒度必须要拿捏到位。一个页面如果没有组件分割，当页面内容变的丰富之后，开发和维护的成本都会变得十分巨大。如果组件过渡分割，面对巨量的文件和离散的逻辑，开发的难度也会上升。如何拿捏组件的分割粒度，是前端开发中需要考虑的问题。

### 组件分割的必要条件

1. 可复用的UI或者逻辑  
  在Vue的官网中，对组件进行了如下定义： `组件允许我们将 UI 划分为独立的、可重用的部分，并且可以对每个部分进行单独的思考。` 我们将开发过程中需要重复使用的部分进行封装和复用，来加速开发的进度，同时当组件需要修改时，也不需要对多处文件进行变动。UI的复用本质上也是逻辑的复用，因为UI总是承担着逻辑的展示。何种程度的复用规模才需要进行复用呢，这需要根据程序员的心智负担决定。 当一个组件只有寥寥几行，不承担逻辑功能，即便被多处引用，我个人更推荐使用编辑器的代码缩写补全来进行填充，而不是使用组件，这往往会加重框架的负担。

2. 对过量逻辑的拆分  
  当一个组件文件变得过于臃肿时，我们往往需要对组件进行拆分。设想以下，一个拥有着若干个标签页的页面，若果不进行分割，所有子页面的UI/数据和逻辑全部堆砌在一起，一个文件有两三千行，光是空白数据变量都有着几百行代码，对这种工程进行修改和迭代，有多少痛苦。
  这时候往往需要根据UI承担的功能进行子组件的划分。  
  例如，在一个布局文件中存在头部，尾部，侧边栏和主体部分，这些部分不需要被其他文件复用，不满足第一条原则。但是这些部分的UI 往往承担着不同的数据和逻辑，当这些部分仅仅只是简单的UI时，我们可以保留他们的状态不进行分割，当这些部分承担着复杂的逻辑时，我们就可以对这部分进行拆分。  
  注意：被分割的组件内部必须有着强相连逻辑，组件与组件之间必须只有弱相连逻辑。

3. 由框架决定的对性能的优化  
  框架会带给我们一定的局限性，我们的代码必须得符合框架的内在逻辑。例如在react组件中，一个数据的变化必然会引起整个组件的重新渲染，此时需要对组件进行粒度拆分，封装数据流，减少数据变动带来的组件更新。这部分的拆分也必须保证逻辑的相关性不被打破，通常在进行上面两条规则时，组件粒度已经得到了保证。
